# M1 — the Route Prover

Branch `wave1/prover`. Implements ADR 005 §1 and §2: a prover that decides
whether a level is playable by **playing it** with the shipping movement code,
hop by hop along a declared route, and writes the button presses that did it.

Nothing in here models movement. The search calls `form.update()` and
`actor.step_motion()` on the real `Actor` and the real `FormBase` subclass at
60 Hz. The first thing I measured was the number ADR 005 quotes as proof that
the old model was wrong:

```
frog   apex 85.42 px = 5.339 tiles      <- tools/reachability.py says 5.16
human  apex 46.67 px = 2.917 tiles      <- the model says 2.78
fish   apex 13.75 px = 0.859 tiles      <- the model says 0.78
```

5.339 against the ADR's measured 5.34. The harness is driving the game.

---

## What I built

| File | What it is |
|---|---|
| `tools/solver/prove.tscn` + `prove.gd` | The tool. A one-node headless **scene**, not `--script`, because the form scripts reference `AudioManager` and `--script` has no autoloads. CLI, route input, hop loop, failure reporting, tape writing. |
| `tools/solver/sim.gd` (`ProverSim`) | The real `Actor` + `FormBase` stepped one tick at a time, plus the entity layer: pads, keys, doors, switches. Snapshot/restore for the search. |
| `tools/solver/search.gd` (`ProverSearch`) | One hop: the 18-action set in 4-frame macros, best-first on manhattan distance, as ADR 005 specifies. |
| `tools/solver/tape.gd` (`ProverTape`) | `levels/<id>.tape.json` read/write, `source_sha`, staleness, and the decoder the replay tier needs. |
| `tools/prove.sh` | Exit **0** all proved, **1** a hop failed, **2** a level declared no route. |
| `tests/fixtures/` | The six historical defects as tiny levels, each with a repaired twin, plus a no-route case. Generated by `make_fixtures.py`. |
| `tests/test_prover_fixtures.gd` | Asserts the prover fails all six and passes all six twins. |
| `tests/test_prover_tape.gd` | Tape encoding, and that a stale tape **fails**. |

Every file is inside my ownership. I edited nothing else.

## The six defects

This is the part that decides whether the gate is worth anything. Measured at
`--budget 8000`:

| Fixture | Defect | Broken | Repaired twin |
|---|---|---|---|
| `a_vine_no_exit` | vine top with no standable exit | **fail** | pass, 33 expansions |
| `b_oneway_headroom` | one-way platform, 16 px of headroom, 22 px player | **fail** | pass, 27 |
| `c_short_door` | door in a passage one tile tall | **fail**, closest 4.0 px | pass, 23 |
| `d_fish_bank` | fish cannot clear the bank | **fail**, closest 16.0 px | pass, 84 |
| `e_sealed_spawn` | spawn sealed behind a 20-tile wall | **fail** | pass, 14 |
| `f_capped_shaft` | shaft capped across its full width | **fail**, closest 16.0 px | pass, 7 |

**The twins are the mutation test.** A fixture that fails on its own proves
nothing — a typo in its route, a misplaced entity or a broken command line
would fail it just as convincingly, and the suite would look green while
testing nothing. Each twin is the same level with the smallest possible repair
(one row of tiles, one tile of headroom, one lower bank) and must pass. A
fixture that fails while a one-tile-different twin passes in 7–84 expansions
can only be failing for the reason it was built to fail for.

I found two real bugs in my own fixtures this way, both caught by a twin that
would not prove: fixture (b) was built with *zero* headroom rather than one
tile, and fixture (a)'s repair put a walkway at a height you could not step
onto.

Two things worth being exact about:

**`d_fish_bank` does not reproduce the original 16 px bank, and cannot.**
`data/forms/fish.json` sets `surface_hop` to -210 px/s, which against gravity
900 gives about 24 px of rise — so the historical 16 px bank is clearable today
and a fixture at that height would *pass*. Measured: a bank one tile (16 px)
proud of the water clears in 84 expansions; two tiles (32 px) does not clear at
8000. The fixture is built at two tiles and its twin at one, so the pair
straddles the real margin. Calling it a "16 px bank" would have been a false
claim.

**At the test budget the fixtures fail by budget, not by frontier exhaustion.**
Frontier exhaustion — "no route exists for this action set" — is the stronger
result, and I only get it on the smallest fixture:

```bash
tools/prove.sh --no-tape --budget 40000 \
  --level-file res://tests/fixtures/b_oneway_headroom.json
# frontier exhausted after 23567 expansions — no route exists for this action set
```

The others have too many reachable states (position bucketed to the pixel,
velocity to 8 px/s) to exhaust at any budget a test suite can afford. So what
the suite asserts is "failed at 8000 expansions, while the twin succeeded in
7–84" — roughly two orders of magnitude of headroom, which is strong evidence
but is **not** a proof of impossibility. I would rather say that than imply it
is proved.

## Measured behaviour on real levels

**`jungle_2` is proved end to end** — keys, doors and all — with the route
supplied on the CLI:

```bash
tools/prove.sh --no-tape --route "spawn>key_yellow:human,key_yellow>door_yellow:human,\
door_yellow>key_red:human,key_red>door_red:human,door_red>exit:human" jungle_2
# PROVED jungle_2 - 5 hops, 732 frames, 31063 expansions
```

732 frames is 12.2 seconds of play, and those are the literal button presses.

**`jungle_4` exercises the transform pads**, which is the case the old blind
search never even reached:

```bash
tools/prove.sh --no-tape --mark "shaft_foot:14,25" \
  --route "spawn>pad_frog:human,pad_frog>shaft_foot:frog,shaft_foot>gem#0:frog" jungle_4
# PROVED jungle_4 - 3 hops, 186 frames, 47 expansions
```

Hop decomposition is not an optimisation, it is the reason the thing
terminates. `jungle_2`, same level, same search:

```
blind, spawn > exit          FAILED at 50000 expansions, closest 502 px
hop-decomposed, 5 hops       129 + 10 + 30881 + 15 + 28 expansions, PROVED
```

Throughput is bounded by the real physics, at **16,300–22,200 ticks/s** (the
spread is eight agents sharing this machine). One expansion is 18 actions x 4
frames = 72 ticks, so about 230–300 expansions/s. Micro-optimising the prover
around that is pointless; I tried, and the profile says the cost *is*
`form.update()` + `step_motion()`, which is the whole point. **Expansion counts
are deterministic and machine-independent — quote those, not seconds.**

## What I could NOT verify

1. **No level is proved *by the gate*, because no level declares a route yet.**
   `jungle_2` is proved end to end and `jungle_4` part-way, but only with the
   route passed on the CLI — which is what `--route` exists for. `route` in
   `levels/*.json` is the routes agent's deliverable and I did not add one, the
   file is not mine. So `tools/prove.sh` with no arguments currently exits **2**
   for every level, which is correct behaviour ("silence is not a pass") and not
   a passing gate. `jungle_1`, `jungle_3` and `jungle_5` have had no route
   written for them at all and are unproved.

2. **No tape is committed.** I generated and verified tapes (including
   `--verify-tapes` on a real level) and then deleted them. A tape's
   `source_sha` binds it to the exact level bytes, so any tape I wrote now
   would go stale the instant the routes agent adds a `route` key. Whether
   tapes are committed or generated in CI is a decision for the routes and
   replay agents; I have no opinion I can back with evidence.

3. **The replay half of ADR 005 §3 is not mine and is untested end to end.** I
   ship the decoder (`ProverTape.frames()` / `.apply()`), and
   `tests/test_prover_tape.gd` exercises it, but nothing has yet fed a tape
   through the real `Level` and asserted completion. Until that exists, the
   prover proves geometry and nothing has proved the *level*.

4. **Enemies, damage and the screen flip are not simulated.** ADR 005 says so
   explicitly, and this is the honest limit: the tape may walk straight through
   a walker.

5. **Breakable crates are treated as permanently solid.** The prover carries no
   weapon (see *Deviations*), so a crate is a wall to it. This can only cause a
   false *failure*, never a false pass, and the tool now says so in the failure
   output whenever the level has breakable tiles. I did not verify whether any
   existing level's intended route goes through a crate.

6. **`jungle_5` cannot be fully proved.** It has `boss_exit` and no `exit`: the
   gate only appears once the Grove Warden dies. The prover can target
   `boss_exit` as a waypoint, which is ADR 005's boss check 5 ("it ends"), but
   the fight itself needs the Boss Gate.

7. **Definition-of-done items 4 and 5 are not done, deliberately.** There is no
   screenshot because the prover renders nothing, and `shots/` is not my file.
   `CHANGELOG.md` is not mine either, so it does not mention this work — please
   fold it in at merge.

8. **The half-frame question.** In the game each trigger is a `Node2D` with its
   own `_physics_process`, so whether a pad fires before or after the player
   moves depends on tree order. The prover tests contacts *after* the move, in
   the same frame. I could not find a case where this changes an outcome, and I
   did not prove there isn't one.

## Deviations from ADR 005, and why

**The action set is the 18 combinations; I did not add attack.** The ADR says
"plus attack when the form can". Attack changes the simulation only by breaking
crates, and the blade is a node-driven projectile (`boomerang_blade.gd` plus a
`Projectile`) that I would have had to *model* to run off-tree. A hand-written
blade is the same mistake as a hand-written jump envelope, and it fails in the
dangerous direction: an over-generous blade model produces false **passes**.
Leaving crates solid produces false **failures**, which are loud. The tape
vocabulary still carries `attack`, so adding it later is additive.

**Two prunings make the prover stricter than the game.** Both remove states, so
both can only under-report what is reachable:

- States touching a hazard are rejected, so a proved route is damage-free.
  `--allow-hazard` relaxes it.
- A fish with `air_left <= 0` is rejected. `form_fish.gd` reverts a beached
  fish to human, but only `if p is Player`, and the prover drives a bare
  `Actor`. Rather than let the sim diverge from the game, it refuses the state.

## The failure mode you will actually hit

Greedy best-first on manhattan distance — which ADR 005 fixes — stalls in local
minima when a waypoint is off the natural path. This produces **false
failures**, and it is the thing most likely to waste the routes agent's day.
Two measurements:

```
jungle_2, door_yellow > key_red                    30881 expansions, PROVED
jungle_2, door_yellow > gem#3 > key_red            FAILED at 50000 on hop 1
```

`gem#3` sits up a vine and back to the left; splitting the hop there made it
*harder*, not easier. The same thing the other way round, on `jungle_4`: the
frog has to get from its pad into a walled shaft, and the heuristic climbs the
*outside* of the shaft wall because that reduces the distance fastest.

```
pad_frog > gem#0                            FAILED at 50000, closest 82 px
pad_frog > shaft_foot > gem#0                       47 expansions, PROVED
```

One marker at the foot of the shaft — `--mark shaft_foot:14,25` — is the whole
difference. And in fixture (f), moving the frog pad from the far wall of the
shaft to directly under the gap:

```
pad across the shaft from the gap      4001 expansions
pad under the gap                         7 expansions
```

**Put waypoints where a player would actually go.** If a hop needs more than
~50k expansions it is too coarse (ADR 005), but a badly *placed* waypoint is
worse than a coarse one. `tools/prove.sh --waypoints` lists every id a route
may name in each level, and `--mark name:x,y` lets you try a waypoint from the
command line before committing it to the DSL.

## Assumptions I made about other agents' work

1. **Route format** — `levels/<id>.json` gains
   `"route": [{"from": "...", "to": "...", "form": "..."}]`, exactly as ADR 005
   writes it. I also accept `--route "spawn>pad_frog:human,pad_frog>exit:frog"`
   so I was never blocked on this.

2. **A route is a chain.** Hop 1 must start at `spawn`, and each hop's `from`
   must equal the previous hop's `to`. This is stricter than the ADR states and
   it is deliberate: the prover carries position *and velocity* across the join,
   so the tape is one continuous run of presses. A route with a gap would
   silently teleport Kaya and the tape would not replay. The prover rejects it
   with exit 2. **If the routes agent needs disjoint hops, tell me — it changes
   the tape contract, not just the checking.**

3. **Markers** — `g.mark("shaft_top", x, y)` serialises as either a top-level
   `"markers": [{"name":..., "x":..., "y":...}]` array or an entity of type
   `marker` with a `name`. I accept both; neither exists yet. Markers matter
   more than they look — see the `jungle_4` numbers above. Pickups (`gem`,
   `heart`) are also usable as waypoints, which gives routes free anchors.

4. **Waypoint disambiguation** — several entities of one type resolve to "reach
   any of them". `type#n` picks the nth in level order (`gem#3`).

5. **The replay tier reads `res://tools/solver/tape.gd`.** `ProverTape.frames()`
   returns one action bitmask per frame and **returns empty for a stale tape**;
   `ProverTape.apply(input, bits, prev)` drives an `InputState` with the correct
   press/release edges. Coyote time, the jump buffer and the frog's wall kick
   all read edges rather than held state, so a replay that only sets `jump`
   plays differently. Please use `apply()` rather than rolling it again.

6. **`tools/itest.sh` switching to `--headless`** is someone else's M1 task. I
   did not touch it. It passes as-is (273 checks, exit 0).

7. **The Boss Gate can reuse `ProverSim` and `ProverSearch` directly** for ADR
   005's boss checks 4 (no softlock: run the prover over the arena per phase)
   and 5 (`boss_exit` reachable). `ProverSim.world` is a live `TileWorld`, so a
   phase configuration can be applied before searching.

8. **Environment, not a code change:** `tools/env.sh` is generated by
   `bootstrap.sh` with `PROJECT_ROOT` pointing at the main checkout, so in a
   worktree every `tools/*.sh` runs against `main`'s tree instead of the branch.
   I repointed it at this worktree. The file is gitignored, so this is not in
   the commit — but each agent has to do it, or they are testing the wrong code.
